1.1 Objective

Build a harness with two products. The build control plane reads metric workbooks as untrusted evidence, turns each row into a versioned, machine-validated specification, surfaces every ambiguity and conflict to a named owner, and, only after semantic approval, generates deterministic Python and target-dialect SQL. The runtime data plane executes that approved, versioned code on source data on a schedule, with no model calls and no fresh reading of the workbook.

Success means a metric owner can trace any published number back to a workbook cell, an approved definition version, verified source columns, the exact SQL that produced it, and independently calculated test evidence, and that nothing reached a protected target without a current, authenticated approval that matches the released bytes.

04

Workbook ingestion contract and canonical schemas

The workbook is metadata about metrics: names, definitions, plain-English formulas, Excel formulas and legacy code. It is not the transaction, account or customer data the metrics are computed from (§6 lists the raw data each metric needs). If a sheet does contain observations (for example, a tab of last quarter's reported values), it is profiled and ingested separately under its own ObservationContract and is used only as a reconciliation reference, never as source data.

4.3 Bounds and inclusion rules

Cell rules that preserve evidence

  • Identifiers and leading zeros. Text cells keep their exact string. A numeric cell whose number format pads zeros (for example 000000) yields both raw = 123 and display_text = "000123" with issue ID_NUMERIC_WITH_PAD_FORMAT; the mapping decides which one an identifier field uses.
  • Unicode and multiline code. Strings are stored unmodified (NFC normalization is applied only to a separate normalized copy used for matching). Line endings inside code are preserved.
  • Plain-English formula vs Excel formula vs cached value vs code string. A cell whose openpyxl data_type is "f" is an Excel formula; its cached value comes only from the data_only=True pass. A text cell in a column mapped as formula_text is plain English even if it contains operators. A text cell that parses as SQL or Python is a code string. All four are kept in separate fields.
  • Merged cells. The anchor value is attached to the record that owns the anchor row. Other rows covered by a vertical merge get merged_context = {range, anchor_value} and an issue, not a copied business value. Merged header cells are expanded only into header labels.
  • Hidden content. Extracted and flagged by default, listed in the profile, and excluded from proposals until confirmed. Nothing hidden is dropped silently.
  • Normalization. Header and alias normalization (case-fold, collapse whitespace, strip punctuation) produce normalized_* copies. Originals are never overwritten.

5.3 Model-assisted proposal contract

The model, if approved, sees metadata only: the row's mapped fields, deterministically matched glossary terms, CodeFacts, candidate source column names and short summaries of related approved metrics, within a fixed token budget. It never sees record-level data. Literals in code that match sensitive patterns are replaced with typed placeholders before the call. The model has no tools. Workbook text is passed inside a delimited JSON field labeled as untrusted data; the fixed system instructions say it must never be followed.

Post-validation is deterministic: JSON Schema validation, citation offsets checked against the original text, expression type check, and a rule that a proposal can raise readiness at most to READY_FOR_REVIEW. Cached responses are keyed by (model_id, prompt_version, input_sha256) and are reused only as proposals.

6.6 Medallion layer contracts

Medallion is a logical quality organization. Atomicity and consistency come from the engine, table format and the publication design, not from the layer names.

Bronze: faithful and replayable

  • Source columns as extracted, with types mapped and naive timestamps kept as TIMESTAMP_NTZ, plus an envelope: source system, extraction window, source record ID, op, sequence, batch ID, run ID, schema version, record checksum, extraction and ingestion times.
  • Batches are idempotent by extraction window; re-reading the same window is recorded in the manifest and adds nothing.
  • Rows that cannot be landed (for example a value that does not fit its Delta type) go to bronze_err.malformed_records (restricted) with evidence.
  • Federated reads are not replayable, so Bronze itself is the replay source (ADR-010); its retention bounds how far back a rebuild can go.
  • The metric workbook is versioned separately as harness metadata, never as Bronze data.

Silver: validated and reusable

  • Typing, timestamps kept as stored (TIMESTAMP_NTZ) with derived business dates, key normalization (text, leading zeros kept).
  • Deterministic dedup: survivor = highest source_seq, tie-break by batch and line; same sequence with different content = conflict to quarantine.
  • Current-state tables plus *_versions history tables for restatement and as-of reconstruction.
  • Quarantine only what the authoritative code could not process either (§5.2); everything else is kept and flagged. Reason codes, provenance, owner and replay path; balancing equations prevent unexplained loss.
  • Schema drift: new source columns are logged and ignored until mapped; removed or retyped columns fail the batch.

Gold: dimensional and versioned

  • Atomic transaction fact and periodic snapshot fact at declared grains; conformed dimensions.
  • Metric formulas live once: component measures in facts, ratio logic in generated metric views.
  • Built into the inactive schema of a blue/green pair, validated, then published (§6.8).
  • Freshness, completeness and reconciliation status published with each release.

6.8 Consistent publication on Databricks

Consumers never read Gold tables directly. Each Delta commit is atomic for one table only, and replacing several views is several commits, so the switch is a single-row update that every pub view reads:

  • Two Gold schemas, gold_a and gold_b. Each run first syncs the inactive one from the active one (incremental DEEP CLONE, VERIFY), applies the run's changes, and runs all checks there.
  • Every pub view is a UNION ALL of the same view over both schemas, each branch filtered by ops.publication_state.active_schema.
  • Publishing is one UPDATE of the one-row ops.publication_state table: one atomic commit flips every view.
  • If the workspace supports multi-statement transactions on the warehouse, the switch and its audit row can share one transaction; the design does not require it.

Two things to verify on the real warehouse: that the inactive branch is pruned so queries do not scan both schemas (PF-07, read with EXPLAIN), and that one query reading two pub views sees one snapshot of the pointer table. Consistency test PB-09 runs readers in a loop during a switch and asserts they see the whole old release or the whole new one. Separate queries issued by a dashboard can still straddle a switch; that limit is documented for consumers.

7.4 SCD Type 2 rules

  • Intervals are half-open [effective_from, effective_to) in the same convention as the fact event times. With the synthetic source that is local wall-clock time (TIMESTAMP_NTZ); if Q-16 shows the source stores UTC, intervals use UTC. The open end is 9999-12-31 00:00:00, not NULL.
  • Versions are derived deterministically from Silver history: rows ordered by (valid_from, source_seq); consecutive rows with an equal tracked_hash collapse into one version; each version ends where the next begins.
  • tracked_hash is sha2 over tracked attributes joined with a delimiter that cannot occur in values; Silver enforces non-null tracked attributes.
  • Keys come from identity columns and are persisted. Rebuilds reuse existing keys for the same (account_id, effective_from); tests compare business keys and attributes, not key values.
  • Checks: no overlapping intervals per business key (DI-05), no gaps (DI-06), exactly one current row per key (DI-07), effective_from < effective_to (DI-08, also a Delta CHECK constraint).
  • Late fact, early dimension: handled by the event-time lookup. Late dimension, early fact: the fact load creates an inferred member (is_inferred = true, interval covering all time); when real history arrives, facts that referenced it are re-keyed for their dates and the inferred row is retired.
  • Retroactive corrections: attribute change on an unchanged interval is updated in place (same key, logged in ops.dim_corrections, affected dates rebuilt). Boundary changes flag orphaned versions; facts in the changed range are re-keyed, then orphans are deleted.
  • Wall-clock limitation: in the autumn DST fall-back hour, local times repeat. Ordering inside that hour uses source_seq, and a dimension change inside that hour can attach to the wrong version. Test DI-12 documents the behavior; storing UTC at the source (Q-16) removes it.

Not needed in the slice: bridge tables. Under D-02, MET-0005 counts accounts as its code does, so no account-to-customer bridge is required. If one is added later, it carries [effective_from, effective_to) and an allocation weight summing to 1.0 per account and instant (DI-10). Independent facts are never joined at detail grain; drill-across aggregates each fact to the common grain first.

8.6 Runs, locks, cancellation, restart

  • Run IDs are ULIDs. A parent run (for example package) spawns child runs per step or asset; children inherit the parent's config hash.
  • Concurrency. One writer per workspace (lease lock); one build per bundle; partition-level locks for data-plane writes (asset:<id>:<partition>). Leases expire so a crashed holder does not block forever; a stale holder that wakes up checks its lease before every commit.
  • Cancellation is cooperative: runs.cancel_requested is checked between steps and between statements; the sandbox process group is killed after a grace period. Partial work in an open transaction is rolled back by the engine.
  • Restart (harness resume <run_id>) recomputes each step's input key; a step is skipped only if its key matches and its output artifact verifies by hash. Anything else re-runs. Resume never skips a gate: verification is always repeated against current approvals.

9.1 Generation strategy

  1. Inputs are only the approved specs (by hash), the approved translation rules, the PipelineSpec, the TargetProfile and versioned templates. The workbook is not read.
  2. Metric logic is compiled from the AST to SQLGlot expressions and rendered in the databricks dialect (and duckdb for local tests). Translation rules TR-01 to TR-05 are applied during compilation, not by hand. Scaffolding (DDL, MERGE, REPLACE WHERE, SCD2 steps) comes from small Jinja2 templates whose identifiers pass through a validating quote filter.

  4. Reviewed extensions live in extensions/<name>/<version>/ with their own spec, tests and owner, and are referenced from the AST by name and version.

9.7 CDC apply for silver.txn on Databricks

Each Delta statement commits on its own, so the step first freezes its input in stage.txn_change_set (Bronze columns plus run_id, reason_code, current_seq, current_business_date, is_survivor). Every later statement reads only that frozen set, so a retry after a crash at any point produces the same result (ADR-011). Under D-02 only structural problems are quarantined; status, currency and amount are kept as stored.

9.8 Checkpoints, retries, and the delivery guarantee

  • Never advance past uncommitted data. Each step writes data first and its completion marker last (manifest row, applied-batch row, publication pointer). A marker exists only if everything before it committed.
  • Crash between commits. Because inputs are frozen per run and every write is a keyed MERGE or a REPLACE WHERE, re-running a step after a crash at any point gives the same tables (PB-04, PB-05 inject a failure after each statement).
  • Retries: bounded exponential backoff for transient errors only (warehouse starting, throttling, concurrent-commit conflicts); never for validation or data errors.
  • Concurrency: one writer per pipeline via a lease in the control-plane state; Delta's optimistic concurrency rejects a conflicting commit, which is then retried from the step's frozen input.
  • Guarantee: extraction is at-least-once; Silver and Gold are idempotent per (source record, version), so retries and re-reads produce the same tables. This is demonstrated by PB-02 and PB-03, not claimed as end-to-end exactly-once. Effects outside the targets (exports already read by a consumer) cannot be rolled back.

9.9 Legacy-reference runner

Under D-02 the legacy code's own answer is the strongest independent expected value. The runner, approved per Q-17:

  1. Loads the same synthetic or anonymized fixtures into a non-production copy of the source engine.
  2. Parses each metric's code in the source dialect; refuses anything but a single SELECT; applies TR-01 on the legacy side too, replacing GETDATE() with the same fixed as-of literal used on Databricks.
  3. Runs it under a read-only identity with a statement timeout and a row limit, and stores the result with the engine version and fixture hash.
  4. The Reconciler compares it with the Databricks output at the code's grain, using the metric's tolerance. A difference is a release blocker unless explained by an acknowledged risk or TR-05 tie.

12.3 Generated versus maintained code

  • generated/ is written only by the generator. Every file has a provenance header; harness generate --check in CI fails if any file differs from a fresh generation.

  • Intentional edits never stay in generated/. They become either a spec change (reviewed at the semantic gate) or a reviewed extension module in extensions/ referenced from the AST.
